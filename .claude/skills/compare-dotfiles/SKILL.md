# Compare this repository with another dotfiles repository

この構成は ryoppippi/dotfiles の影響を受けて育ってきた。`check-dotfiles-updates` が
「前回からの差分」を時間軸で追うのに対し、こちらは**今この瞬間の全体差分**を空間軸で見る。
コミットの履歴は使わず、両方のツリーをそのまま突き合わせる。

- 比較先: 引数で指定。省略時は `ryoppippi/dotfiles`
- 判断の記録: `decisions.md`（このディレクトリ、git 管理）。**採らないと決めたものを残す**
- 報告先: `artifact.json`（このディレクトリ、git 管理外）。同じページを更新するための URL

## 手順

1. 比較先の clone を最新にする。パスは `$(ghq root)/github.com/<repo>`。無ければ
   `check-dotfiles-updates` と同じ blobless clone で取得する。

2. **`decisions.md` を読む。** ここに載っているものは提案し直さない。載っているのに状況が
   変わった（相手が方式を変えた、こちらの前提が変わった）ときだけ、「記録ではこうだが」と
   添えて再提示する。

3. **構成の差分を出す。** ファイル一覧を領域ごとに突き合わせ、片側にしかないものを両方向で
   出す。コマンドは [`references/commands.md`](references/commands.md) の「手順3」。

   領域は相手のツリーに合わせて決める（`nix/modules/`、`agents/skills/`、`agents/shared/`、
   `claude/`、`codex/`、`fish/`、`nvim/` など）。**相手の構成をそのまま正とはしない。**

4. **両方にあるものを比べる。** 同じ役割のファイル（パスが一致するもの、名前が同じ skill、
   同じツールのモジュール）だけを対象に、実際に diff を取る。報告するのは全文ではなく:
   - こちらが宣言していないキー、値が違うキー
   - 仕組みの違い（生成／コピー／マージ、bash／Nushell、宣言型／手続き型）

   **指示文（`CLAUDE.md`、`AGENTS.md`、共有断片、rules、同名の skill）は本文まで読む。**
   見出しの一致や行数の比較で終わらせない。同じ見出しの下で中身が入れ替わっていることがある。
   報告は2つに分ける:
   - **片方にしかない指示** — 内容として存在しないもの。取り込み候補になるのはこちら
   - **同じ指示の書き方の違い** — 箇条書きか節か、長いか短いか。中身が同じなら提案にしない

   **相手が削った指示も情報として扱う。** エージェントへの指示はモデルの変化に合わせて
   増減する。以前は書く必要があったことが不要になった、逆に新しく必要になった、という判断の
   痕跡なので、「向こうには無い」を機械的に「こちらが充実している」と読まない。どちらの向きの
   差分も、なぜそうなったかを一度考えてから仕分ける。

5. **仕分ける。** 差分は全部が取り込み候補ではない。次の3つに分ける。
   ただし `agents/skills/` だけは既定が逆になる。下の「skill の既定」を先に読むこと:
   - **取り込む価値があるもの** — 向こうにしかない仕組みで、こちらの困りごとに当たるもの
   - **意図的に違うもの** — こちらが理由を持って選んでいるもの。**コメントに理由が書いてあれば
     それを引用する**。`decisions.md` にあるものもここ
   - **こちらが先行しているもの** — 向こうに無い、または向こうが後から入れたもの

6. **提案する。** 取り込む価値があるものだけを、**何を解決するか**と**移植のコスト**を添えて出す。
   相手の語彙・モデルの好み・持っていないツールへの参照は落とし、仕組みだけを移す
   （ユーザーが「まんま持ち込む」と言った場合を除く）。

7. **結果を Artifact のページにまとめる。** チャットには提案の見出しだけを書き、詳細はページに置く:
   - 領域ごとの構成差分（片側にしかないもの、両方向）
   - 同じ役割のファイルの比較（相手の値 / こちらの値）
   - 仕分けの3分類
   - 提案

   `artifact.json` に URL があれば同じページを更新し、無ければ新規に作って URL を書き込む。
   ページを書く前に `artifact-design` skill を読むこと。

   `Artifact` ツールが無い環境（Codex など）では、同じ内容をリポジトリの外（`$TMPDIR` など）に
   HTML で書き出して内蔵ブラウザで開く。`artifact.json` は触らない。

8. **`decisions.md` を更新するか聞く。** 提案を見送ったもの、採ったものを1行ずつ追記する。
   書くのは「何を・いつ・なぜ」。次回この skill を動かしたとき、手順2でこれを読んで蒸し返さない。

## skill の既定は「向こうに合わせる」

`agents/skills/` は ryoppippi から derive したもので、こちらが手を入れたのは一部だけ。
差分を見つけたら、**既定は向こうに揃える**。残すのは次の両方を満たすときだけ:

1. こちらにしか無いものを指している — herdr、worktrunk（`wt`）、hunk、`codex-review-gate`、
   `nix run .#<app>`、公開リポジトリ方針、Nushell 既定、`gh-nix`、`merge-config`、
   このリポジトリのパス、こちらのモデル選択
2. **その理由が commit メッセージか `decisions.md` に記録されている**

2 は必ず `git log --format='%h %s' -- agents/skills/<name>` で辿り、本文まで読んで確かめる。
理由が見つからなければ drift として扱い、向こうに寄せる。**「こちらのほうが厚い」は理由ではない。**

差分は4つに分ける:

- **こちらが理由を持って変えた** — 上の1と2を両方満たす。残す
- **向こうが新しい** — 向こうのほうが厚い、または良い。機械固有の話ではない。取り込む
- **向こう固有** — 向こうにしか無いものを指している。そのままでは入らない。仕組みだけ読み替えるか、落とす
- **表記だけ** — 意味が同じ。揃えるついでに寄せる

**参照先が実在するかを両側で確かめる。** `ls` と `rg` で当たってから「模範として指している」と書く。
上流の skill が上流でも古くなっていることがあり、その skill を足しても参照は直らない。

揃えたあと、残した差分は手順8で `decisions.md` に「意図的に違う」として理由付きで書く。
次回ここを読むので、書かなければ同じ判定をやり直すことになる。

## 注意

- **相手に合わせることが目的ではない。** この構成が先行している領域（herdr、worktrunk、
  hunk など）は、差分ではなく「向こうに無い」という事実として扱う
- 差分が大きい領域（`nix/modules/` 全体など）は、ファイル数と代表例だけを出して、
  どこを深掘りするか聞く。全ファイルの diff をページに貼らない
- 相手のリポジトリは相手の機械のためにある。マシン固有の設定（ホスト名、鍵、仕事の環境、
  持っていないハードウェア）は最初から候補にしない
- `check-dotfiles-updates` と役割が重なる部分（ツールの採用数、commit の追跡）はこちらでは
  やらない。動向はあちら、全体差分はこちら
